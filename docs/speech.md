### Слайд 1 — Титульный

Уважаемые члены государственной экзаменационной комиссии! Разрешите представить выпускную квалификационную работу на тему «Разработка прототипа сервиса по выбору научного руководителя для выпускных квалификационных работ в высшем учебном заведении».

### Слайд 2 — Актуальность и цель

В большинстве российских вузов процесс выбора научного руководителя и темы ВКР по сей день организован вручную: бумажные заявления, переписка по электронной почте, разрозненные таблицы. Отсутствует единый цифровой инструмент, в котором студент, преподаватель и заведующий кафедрой могли бы видеть актуальный статус заявки в реальном времени и взаимодействовать в рамках единого регламентированного процесса.

Цель работы — повысить эффективность этого процесса за счёт разработки прототипа автоматизированной программно-информационной системы выбора научного руководителя и темы ВКР.

### Слайд 3 — Задачи

Для достижения поставленной цели решён ряд задач: от анализа предметной области и сравнения существующих решений до проектирования архитектуры, реализации двухэтапного согласования заявок, разработки модуля коммуникации и подсистемы уведомлений, а также автоматизированного тестирования системы.

### Слайд 4 — Выявленные проблемы

Анализ предметной области выявил пять ключевых проблем. Первая — нет регламентированного процесса с прозрачными статусами: ни один участник не имеет единой точки контроля. Вторая — ручной учёт создаёт риск одновременного захвата одной темы несколькими студентами. Третья — обсуждение ведётся в сторонних мессенджерах, и история переписки никак не привязана к конкретной заявке. Четвёртая — каждый отказ вынуждает заново оформлять документы. Пятая — сводная аналитика требует ручной агрегации данных из разных источников.

### Слайд 5 — Анализ существующих решений

Рассмотрены три класса решений: Moodle, ELMA365 и Битрикс24, 1С:Университет. Сравнение по восьми критериям показало: ни одно не перекрывает весь необходимый набор. Moodle не имеет регламентированного процесса заявки и архива ВКР. Корпоративные платформы сложны во внедрении и не специализированы под задачу ВКР. 1С:Университет не предусматривает встроенный чат. Разрабатываемая система по всем восьми критериям получает оценку «удовлетворён».

### Слайды 6–7 — Требования и стек

На основе анализа сформулированы требования. Функциональные: четыре роли пользователей, двухэтапный жизненный цикл согласования, чат, архив ВКР, уведомления, аналитика и экспорт. Нефункциональные: безопасность на основе JWT с ротацией refresh-токенов, масштабируемость за счёт stateless-серверной части, переносимость через Docker-контейнеры.

Технологический стек: серверная часть — ASP.NET Core 10 на C# 13; клиентская — Angular 20 с библиотекой PrimeNG; хранение данных — PostgreSQL 16, Redis для сессий, MinIO для файлов; развёртывание через Docker Compose с Nginx.

### Слайд 8 — Архитектура

Архитектура построена по принципам Clean Architecture и состоит из четырёх слоёв. Domain содержит сущности и бизнес-правила без каких-либо внешних зависимостей. Application реализует прецеденты использования через интерфейсы репозиториев. Infrastructure предоставляет конкретные реализации — EF Core, Redis, MinIO, SMTP. API-слой отвечает за контроллеры, JWT-middleware и конфигурацию инверсии зависимостей. Такое разделение обеспечивает независимую тестируемость бизнес-логики.

### Слайд 9 — Диаграмма вариантов использования

Диаграмма вариантов использования фиксирует более двадцати прецедентов для четырёх ролей: студента, преподавателя, заведующего кафедрой и администратора.

### Слайд 10 — Схема базы данных

Реляционная модель данных PostgreSQL включает девять ключевых сущностей. Отдельно выделены таблицы для журнала переходов статусов, чат-сообщений, уведомлений и архива защищённых работ. Схема инициализируется набором SQL-скриптов; EF Core работает поверх готовой схемы без собственных миграций — это сохраняет единый источник истины для структуры базы.

### Слайды 11–12 — Жизненные циклы

Центральной частью системы являются два последовательных жизненных цикла. В первом студент отправляет запрос на научное руководство одному или нескольким преподавателям. Ключевое бизнес-правило: при одобрении запроса все прочие активные запросы этого студента к другим преподавателям автоматически отменяются в рамках одной транзакции. Это исключает ситуацию двух одновременных научных руководителей.

Второй жизненный цикл — заявка на тему ВКР — проходит двухэтапное согласование: сначала научный руководитель переводит заявку в статус ожидания, затем заведующий кафедрой принимает финальное решение. Студент может как выбрать тему из каталога, так и предложить собственную. На всём протяжении процесса студент и преподаватель общаются через встроенный чат, привязанный к конкретной заявке, — история переписки сохраняется в системе.

### Слайды 13–18 — Интерфейс

Обратимся к реализованному веб-интерфейсу. Страница авторизации обеспечивает вход по email и паролю. Раздел тем позволяет студенту просматривать и фильтровать доступные темы с возможностью сразу перейти к странице преподавателя, где видны его специализация, лимит студентов и статистика ВКР из архива. Форма создания заявки позволяет выбрать тему из каталога либо предложить собственную. Страница самой заявки отображает актуальный статус, полную историю переходов и открытый чат. Наконец, раздел аналитики для заведующего кафедрой наглядно показывает текущее состояние заявок по кафедре.

### Слайд 19 — Тестирование

Система покрыта несколькими уровнями тестов. Unit-тесты проверяют переходы жизненных циклов и разграничение прав по ролям — в том числе граничные случаи, такие как попытка несанкционированного действия. Интеграционные тесты на базе Testcontainers выполняются на реальных экземплярах PostgreSQL и Redis и охватывают полный сценарий от регистрации заявки до утверждения. Отдельно верифицированы конкурентные операции: одновременные заявки нескольких студентов на одну тему. Все тесты проходят успешно.

### Слайд 20 — Заключение

В результате выполнения работы разработан функциональный прототип AcademicTopicSelectionService, реализующий полный цикл: от выбора научного руководителя до хранения защищённой работы в архиве. Система специализирована под задачу ВКР и объединяет в одном веб-сервисе регламентированный процесс согласования, встроенный чат и аналитику — то, чего в совокупности не предлагает ни один из рассмотренных аналогов. Работа выполнена в полном объёме.
