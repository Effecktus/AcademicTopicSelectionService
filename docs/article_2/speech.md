## Слайд 2 — Цель и задачи (~50 сек)

В высших учебных заведениях распределение тем ВКР и научных руководителей часто сопровождается разрозненными каналами связи: электронная почта, личные договорённости, отдельные таблицы. Участники процесса не видят единого актуального статуса. Целостный веб-сервис требует устойчивой архитектуры, допускающей развитие без переписывания бизнес-логики.

Цель работы — спроектировать и обосновать архитектуру такого сервиса с учётом четырёх ролей: студент, преподаватель, заведующий кафедрой и администратор.

Для достижения цели решались задачи: определение границ сервиса, обоснование технологического стека, описание слоистой архитектуры, ключевых потоков данных и подходов к безопасности.

---

## Слайд 3 — Технологический стек (~50 сек)

Технологический стек определялся исходя из требований к масштабируемости и сопровождаемости.

**Клиентская часть** — SPA на Angular и TypeScript с компонентной библиотекой PrimeNG: единый интерфейс для всех ролей, маршрутизация, формы и HTTP-вызовы API.

**Серверная часть** — ASP.NET Core с C#: REST API, внедрение зависимостей, авторизация, ORM.

**Хранение данных**: PostgreSQL обеспечивает целостность и транзакционную смену статусов заявок; Redis — данные с ограниченным сроком жизни (refresh-токены); S3-совместимое хранилище — файлы архива ВКР.

Уведомления дублируются в базе данных и при необходимости отправляются по SMTP через MailKit.

---

## Слайд 4 — Общая архитектурная схема (~60 сек)

На схеме представлена логическая архитектура сервиса. Принята модель «клиент — сервер»: представление полностью в браузере, вся проверка прав, бизнес-логика и доступ к данным — на сервере; обмен по HTTPS в формате JSON.

Сервер построен по принципам чистой архитектуры: зависимости направлены к центру. Домен не зависит от фреймворков и СУБД — это принципиально упрощает тестирование переходов статусов заявки и ролевой модели.

Ключевое архитектурное решение: интеграции с внешними системами вуза — ЭИОС, LDAP — подключаются через слой Infrastructure и не затрагивают доменные правила согласования.

---

## Слайд 5 — Структура сервера. Декомпозиция (~60 сек)

Серверное приложение разбито на четыре проекта.

**Domain** — сущности и бизнес-правила без каких-либо зависимостей от EF Core или ASP.NET Core.

**Application** — сервисы заявок, тем, чата, уведомлений и аутентификации; здесь определены интерфейсы репозиториев.

**Infrastructure** — конкретные реализации: DbContext с EF Core, Redis, S3, SMTP.

**API** — контроллеры по маршруту `/api/v1/...`, JWT middleware и конфигурация Swagger.

Зависимости: API и Infrastructure ссылаются на Application и Domain; Application ссылается только на Domain; Domain автономен.

Функционально сервис декомпозирован на семь подсистем: управление доступом, справочники, каталог тем, процесс согласования заявок, коммуникации, уведомления и архив.

---

## Слайд 6 — Потоки данных и безопасность (~50 сек)

**Потоки данных.** Заявки передаются как JSON через REST API, обрабатываются в Application и фиксируются транзакцией в PostgreSQL. Чат реализован через периодические запросы к API без постоянного WebSocket-канала — это снижает требования к сетевой инфраструктуре вуза и упрощает прохождение трафика через межсетевые экраны. Файлы архива хранятся в S3, метаданные — в PostgreSQL.

**Безопасность** обеспечена JWT-аутентификацией с ротацией refresh-токенов в Redis, хэшированием паролей, ролевым доступом на уровне API и сервисов, серверной валидацией, CORS только для доверенных источников.

Концентрация правил переходов статусов в Domain и Application позволяет тестировать их модульно, без обращения к реальной СУБД.

## Слайд 7 — Заключение (~25 сек)

Таким образом, спроектирована архитектура, сочетающая клиент-серверную модель с четырёхслойным сервером по принципам чистой архитектуры. Бизнес-правила локализованы в Domain и Application, изменения в отдельных подсистемах не затрагивают ядро. Сервис устраняет разрозненность коммуникаций и предоставляет участникам единое представление о статусе заявок.
