**АРХИТЕКТУРА СЕРВИСА ВЫБОРА ТЕМ ВЫПУСКНОЙ КВАЛИФИКАЦИОННОЙ РАБОТЫ**

**ARCHITECTURE OF THESIS TOPIC SELECTION SERVICE**

*Аннотация: Представлена архитектура веб-сервиса выбора темы и научного руководителя выпускной квалификационной работы в вузе. Обоснован стек Angular, ASP.NET Core, PostgreSQL, Redis, S3 и SMTP. Кратко изложены клиент-серверная модель, слои по чистой архитектуре, функциональная декомпозиция, потоки данных и безопасность.*

*Ключевые слова: архитектура, веб-сервис, чистая архитектура, REST API, веб-приложение, автоматизация.*

*Abstract: The architecture of a web service for thesis topic and supervisor selection at a university is presented. The Angular, ASP.NET Core, PostgreSQL, Redis, S3 and SMTP stack is justified. The client-server model, clean-architecture layers, functional decomposition, main data flows, and security are outlined.*

*Keywords: architecture, web service, clean architecture, REST API, web application, automation.*

В высших учебных заведениях распределение тем выпускных квалификационных работ и научных руководителей часто сопровождается разрозненными каналами связи и слабой прозрачностью статусов. Целостный веб-сервис требует устойчивой архитектуры, допускающей развитие без переписывания бизнес-логики \[1, с. 28--41; 2, с. 35--52\].

Цель работы --- спроектировать и обосновать архитектуру веб-сервиса для автоматизации выбора темы и научного руководителя выпускной квалификационной работы с учётом ролей студента, преподавателя, заведующего кафедрой и администратора.

Задачи: определить назначение и границы сервиса; обосновать технологический стек; описать архитектурную схему и декомпозицию на подсистемы; изложить структуру серверного приложения и ключевые потоки данных; сформулировать подходы к безопасности.

**1. Назначение и границы сервиса**

Сервис поддерживает организационный контур выбора темы выпускной квалификационной работы и научного руководителя. Участники: студент, преподаватель, заведующий кафедрой, администратор; ключевые сущности --- кафедра, тема, заявка студента, архив защищённых работ. Реализованы учёт и согласование заявок по маршруту «преподаватель → заведующий кафедрой», переписка по заявке до финального решения заведующего, справочники, загрузка файлов архива, уведомления о событиях и смене статуса заявки.

Границы решения: веб-клиент, сервер с REST API, PostgreSQL, Redis, S3-совместимое объектное хранилище, SMTP. Интеграция с электронно-информационной средой вуза, LDAP и корпоративным мониторингом не входит в объём работы; предусмотрена возможность добавления адаптеров без изменения доменных правил согласования.

**2. Технологический стек**

Клиент --- SPA на Angular и TypeScript (SCSS): единый интерфейс для ролей, маршрутизация, формы, HTTP-вызовы API. Сервер --- ASP.NET Core и C#: REST API, внедрение зависимостей, авторизация, ORM, Swagger (OpenAPI). PostgreSQL обеспечивает целостность и транзакционную смену статусов заявок; Redis --- данные с ограниченным сроком жизни (refresh-токены); файлы архива --- в S3-совместимом хранилище (в том числе MinIO); уведомления дублируются в БД и при необходимости отправляются по SMTP.

**3. Общая архитектурная схема**

Модель «клиент --- сервер»: представление в браузере; проверка прав, бизнес-логика и доступ к данным --- на сервере; обмен по HTTPS (JSON). Сервер следует принципам чистой архитектуры: зависимости направлены к центру, домен не зависит от фреймворков и СУБД, что облегчает проверку переходов статусов заявки, чата и ролевой модели \[1, с. 95--112; 2, с. 35--52\]. Логическая схема взаимодействия браузера, SPA, REST API, слоёв Application и Domain, PostgreSQL, Redis, объектного хранилища и SMTP приведена на рисунке 1.

**4. Декомпозиция на подсистемы**

Выделены подсистемы: управление доступом и профилями (JWT, роли, регистрация администратором); справочники; каталог тем; процесс заявок с проверкой роли и статуса; коммуникации по заявке до решения заведующего; уведомления (интерфейс, почта); архив и администрирование (метаданные, файлы, отчётность).

**5. Внутренняя структура сервера**

Четыре проекта: Domain (сущности, аудит, без зависимостей от EF Core и ASP.NET Core); Application (сервисы заявок, тем, чата, справочников, уведомлений, аутентификации, DTO, интерфейсы репозиториев); Infrastructure (DbContext, EF Core, Redis, S3, SMTP); API (контроллеры /api/v1/\..., middleware, Swagger, вызов сервисов Application без дублирования правил). Зависимости: API и Infrastructure → Application и Domain; Application → Domain; Domain автономен (в репозитории: AcademicTopicSelectionService.\*), что соответствует идее разделения уровней и инверсии зависимостей относительно домена \[1, с. 95--112; 2, с. 35--52\]. **6. Потоки данных, хранение и безопасность**

Заявки: JSON в REST API, делегирование сервису Application, транзакции в PostgreSQL при смене статуса. Чат: сообщения в БД по заявке; доставка через периодические запросы к API (polling) без постоянного канала WebSocket, что снижает требования к сетевой инфраструктуре вуза и упрощает прохождение трафика через межсетевые экраны. Архив: объекты в хранилище, метаданные в PostgreSQL, доступ по роли администратора. Аутентификация: refresh-токены в Redis. Персистентные данные согласованы с Entity Framework Core; детали концептуальной и логической модели --- в проектной документации по БД. Реализованы ролевой доступ на API и в сервисах, JWT и refresh, хэширование паролей, серверная валидация, Problem Details, журналирование ошибок, CORS для доверенных источников в соответствии с практиками платформы \[4\]. Сосредоточение правил переходов статусов заявки и проверок ролей в слоях Domain и Application при неизменных контрактах репозиториев облегчает модульное тестирование без обращения к реальной СУБД и внешним сервисам.

**Заключение**

Архитектура сочетает клиент-серверную модель с четырёхслойным сервером по принципам чистой архитектуры, покрывает подсистемы предметной области и опирается на PostgreSQL, Redis, S3-совместимое хранилище и SMTP. Достигнуты модульность, локализация бизнес-правил в домене и Application, возможность расширения интеграциями (ЭИОС, LDAP) через Infrastructure без перестройки ядра; исходный код представлен в репозитории проекта \[3\].

Практическая значимость решения --- в сокращении объёма неформальной переписки при согласовании темы и в предоставлении заведующему кафедрой и участникам процесса единого актуального представления о статусе заявок. Описанное разделение слоёв снижает риск регрессий при доработке отдельных подсистем (например, только уведомлений или только загрузки файлов) за счёт локализации изменений во внешних кольцах архитектуры \[1, с. 95--112\]. Текущее ограничение --- отсутствие готовых адаптеров к корпоративным системам конкретного вуза; их добавление относится к слою Infrastructure и не затрагивает доменные сценарии согласования. Перспектива работ --- пилотное использование сервиса на кафедре, сбор замечаний пользователей и уточнение требований к отчётности и интеграциям.
